# ReportCXR

흉부 X선 판독문(MIMIC-CXR · CheXpert)을 **문장 단위의 구조화된 명제**로 바꾸는
파이프라인입니다. 로컬 LLM(Qwen, llama.cpp)이 문장을 읽고, 결정론적 사전·규칙이
표기를 통일하고 검사합니다.

### 이 저장소의 브랜치

세 세대의 코드가 브랜치 하나씩에 들어 있습니다. **처음 보신다면 `main` 만 보시면 됩니다.**

| 브랜치 | 세대 | 무엇 | 상태 |
|---|---|---|---|
| **[`main`](https://github.com/DH82/ReportCXR/tree/main)** | 3세대 (2026-09~) | 명제 파서 + 사전 정규화 + 검증 도구 일체 (이 문서) | **현재 개발본** |
| [`ReportCXR2`](https://github.com/DH82/ReportCXR/tree/ReportCXR2) | 2세대 (2026-08) | *한 발화 = 명제 0~n개* 파서의 첫 판. `main` 의 `Pipeline/`·`Prompt/` 의 전신 | 보관 |
| [`ReportCXR`](https://github.com/DH82/ReportCXR/tree/ReportCXR) | 1세대 (2026-08) | MAPLEZ 논문식 *한 줄 = 소견 하나* 구조화기 (OpenAI API) | 보관 |

### 데이터는 포함되어 있지 않습니다

MIMIC-CXR 은 PhysioNet 자격 인증 데이터라 재배포할 수 없습니다. 그래서 판독문
원문이 들어가는 것 — `jsonl/` 데이터, `out/` 산출물, 검수 시트(`GPT/sheet_*_labeled.tsv`),
API 로그 — 은 전부 저장소 밖(로컬 + 백업)에 둡니다. 코드를 돌리려면 데이터를 직접
받아 같은 자리에 두셔야 합니다. 문서 안의 예시 문장은 설명용 단문입니다.
문서에 나오는 `/home/ldh/...`, `/data3/...` 경로는 원 작업 환경 기준입니다.


## 한 줄로 말하면

**의사가 쓴 흉부 X선 판독문을, 컴퓨터가 셀 수 있는 표 형태로 바꾸는 프로그램**입니다.

---

## 1. 무슨 문제를 푸는 건가요?

의사는 이렇게 씁니다.

```
"Bilateral pleural effusions, left greater than right."
(양쪽 흉수, 왼쪽이 오른쪽보다 많음)
```

사람은 바로 이해합니다. 그런데 **컴퓨터는 이런 문장을 셀 수가 없습니다.**
"흉수가 있는 환자가 몇 명이지?" 를 세려면 문장이 아니라 **칸에 들어간 값**이
필요합니다.

그래서 이렇게 바꿉니다.

| 칸 | 값 | 무슨 뜻 |
|---|---|---|
| 무엇이 | `pleural_effusion` | 흉수(폐 주변에 고인 물) |
| 어디에 | `pleura` (양쪽) | 흉막 |
| 어떤 | 왼쪽 > 오른쪽 | 분포 |
| 있나 없나 | **있음** | |
| 예전보다 | 비교 없음 | |

이렇게 바꿔 놓으면 세는 것도, 찾는 것도, 학습에 쓰는 것도 가능해집니다.

### 근데 왜 어렵죠?

**같은 말을 사람마다 다르게 쓰기 때문입니다.**

```
"No pleural effusion"            흉수 없음
"Pleural effusions are absent"   흉수가 없다
"No evidence of effusion"        흉수의 증거 없음
```

셋 다 같은 뜻인데 글자는 전부 다릅니다. 그대로 옮기면 컴퓨터는 **서로 다른
세 가지**로 셉니다. 그래서 **표기를 하나로 통일하는 작업**이 반드시 필요합니다.

## 2. 어떻게 만드나요? — 일꾼 셋이 차례로

이 프로그램은 **세 명이 차례로 일하는 공장**이라고 생각하면 쉽습니다.

```mermaid
flowchart LR
    U["판독문 문장"] --> A["① 번역가 (AI)<br/>문장을 읽고 칸에 나눠 적는다"]
    A --> B["② 교정자 (사전)<br/>표기를 사전대로 통일한다"]
    B --> C["③ 검사관 (규칙)<br/>규칙을 어겼는지 확인한다"]
    C --> R[("완성된 표")]
```

| | 누가 | 무슨 일을 | 특징 |
|---|---|---|---|
| **① 번역가** | AI (Qwen 모델) | 문장을 읽고 칸에 나눠 적는다 | 똑똑하지만 **비싸고**(문장당 30초) **가끔 제멋대로** |
| **② 교정자** | 사전(표) | `왼쪽아래엽` → `아래엽` + `왼쪽` 식으로 표기 통일 | **공짜**, 언제나 **똑같이** 한다 |
| **③ 검사관** | 규칙 44개 | 규칙 어긴 곳을 찾아낸다 | **고치지 않고 지적만** 한다 |

### 이 공장의 제1원칙

> **사전이 할 수 있는 일은 절대 AI에게 시키지 않는다.**

AI는 비싸고, 부를 때마다 답이 조금씩 달라집니다. 110만 문장을 다시 부르려면
이 컴퓨터로는 1년이 걸립니다. 반면 사전으로 고치는 건 **공짜이고 몇 분이면**
끝납니다. 그래서 사전으로 판정할 수 있는 일은 전부 ②·③으로 미룹니다.

**이 원칙 하나가 이 저장소의 구조 전체를 설명합니다.**

## 3. 폴더가 어디에 해당하나요?

```
ReportCXR/
├── Prompt/  Prompt2/            ← ① 번역가에게 주는 "지시서"
├── Pipeline/                     ← ①②③ 을 실제로 돌리는 코드
├── Verify/                       ← 결과가 잘 나왔는지 채점하는 도구
├── Serving/                      ← AI 모델을 띄우는 방법
├── RadLex/                       ← 의학 용어 사전과의 대조 결과
├── GPT/                          ← 결과를 GPT로 한 번 더 감사하는 도구
├── jsonl/                        ← 완성된 데이터 (777MB)
└── out/                          ← 채점표·실험 결과
```

| 폴더 | 쉽게 말하면 | 자세히 |
|---|---|---|
| **`Prompt/`** | AI에게 준 **첫 지시서**. 지금은 안 쓰고 비교용으로만 보관 | [README](Prompt/README.md) |
| **`Prompt2/`** | **지금 쓰는 지시서(v3.4) + 사전(표)**. 사전은 어느 버전을 쓰든 여기 것 하나 | [README](Prompt2/README.md) |
| **`Pipeline/`** | 실제로 돌리는 코드 (①②③) | [README](Pipeline/README.md) |
| **`Verify/`** | 결과 채점. **데이터를 고치지 않고 보기만** 함 | [README](Verify/README.md) |
| **`Serving/`** | AI 모델 띄우기 (docker) | [README](Serving/README.md) |
| **`RadLex/`** | 국제 의학 용어사전과 우리 용어를 맞춰 본 기록 | [README](RadLex/README.md) |
| **`GPT/`** | 기계 검사 → GPT 감사 → 감사자 신뢰도 측정 → 수정안. `run_audit.sh` 로 한 번에 | [audit_records.md](GPT/audit_records.md) |
| `jsonl/` | 완성된 데이터. 용량이 크고 재배포 불가라 git에 안 올림 | — |
| `out/` | 채점표·실험 기록. git에 안 올림 | [README](out/README.md) |

### 왜 지시서가 두 개인가요?

지시서를 고칠 때마다 **AI의 답이 달라집니다.** 그래서 **맨 처음 지시서
(`Prompt/`)** 는 지우지 않고 남겨 둡니다 — 새 지시서가 정말 나아졌는지
**비교하려면 옛것이 있어야** 하기 때문입니다.

지금 쓸 것은 **`Prompt2` (v3.4)** 하나입니다. 예전에는 v3 지시서가 `Prompt3/`
에 따로 있었지만, v2 본문에 패치를 얹는 구조여서 읽으려면 두 파일을 겹쳐 봐야
했습니다. **`Prompt3/` 는 `Prompt2/` 로 합쳤고**, 지시서는 이제 한 편의 완성된
문서입니다. 합치기 전 판본은 git 히스토리에 있습니다.

## 6. 이 저장소가 지키는 약속 넷

코드를 고치기 전에 이 넷만 알면 "왜 이렇게 되어 있지?"의 대부분이 풀립니다.

**① 같은 정보를 두 군데 적지 않는다.**
`왼쪽아래엽`처럼 이름에 "왼쪽"을 넣고 옆 칸에도 "왼쪽"을 적으면, 언젠가 둘이
다른 말을 합니다. 그래서 한 칸에만 적습니다.

**② 근거 없이 고치지 않는다.**
지시서를 고칠 때마다 "몇 건에서 이런 문제가 있었다"는 실제 숫자를 답니다.
그리고 **고치기 전에 "무엇이 얼마나 좋아져야 하는지"를 미리 적어 둡니다.**
안 좋아지면 진단이 틀린 겁니다.

**③ 비교할 수 없는 숫자는 맞대지 않는다.**
사전이 바뀌면 점수도 바뀝니다. 그래서 모든 채점표 맨 위에 **"어떤 사전으로
쟀는지"를 찍어 둡니다.** 그게 다르면 두 점수는 비교 대상이 아닙니다.

**④ 사전이 할 수 있는 일은 AI에게 시키지 않는다.** (§2 참고)
