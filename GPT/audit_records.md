# GPT 검증 도구 — 무엇을 어떤 순서로 하는가

> **한 줄 요약: 기계가 볼 수 있는 것은 기계가 보고(`precheck`), 읽어야만
> 아는 것만 모델에게 묻고(`audit_records`), 그 모델이 얼마나 믿을 만한지를
> 먼저 재고(`goldset`), 그 다음에야 고칠 안을 만듭니다(`repair`).**

---

## 1. 네 개의 프로그램과 그 순서

```
① precheck.py      기계가 100% 정확히 아는 것 → 267건
        ↓            (모델에게는 "이건 묻지 마라"고 알려줌)
② audit_records.py 읽어야만 아는 것만 판정 → flagged.md
        ↓
③ goldset.py       ②가 얼마나 맞는지 채점 (2026-09-16 기준: 별도 모델
                   패스로 채점 — 실제로는 사람이 아니라 모델이 했습니다.
                   사람이 채우면 더 신뢰도가 높지만, 이 도구 자체는 누가
                   채우는지 상관하지 않습니다) → 코드별 정밀도
        ↓            ★ 이걸 건너뛰면 ②의 결과를 쓸 수가 없습니다
④ repair.py        믿을 만한 코드에 한해 수정안 → repairs.md
```

**②와 ④를 나눈 이유**, **③을 먼저 하는 이유**가 이 도구 설계의 전부입니다.
아래에서 하나씩 설명합니다.

## 2. ① `precheck.py` — 기계에게 맡길 것은 기계에게

모델에게 "이 글자가 저 문장 안에 있니?" 를 묻는 것은 두 가지로 손해입니다.

| 손해 | 왜 |
|---|---|
| **돈** | 한 줄 코드로 되는 일에 API 호출을 씁니다 |
| **정확도** | 더 중요합니다. 판정자의 주의력은 한정되어 있습니다. 부분문자열 검사에 주의를 쓰면, **읽어야만 알 수 있는 것에 쓸 주의가 줄어듭니다** |

### 새로 만들지 않고 이미 있는 것을 씁니다

`Pipeline/validate.py` 에 이미 38개 검사가 있습니다. 실제로 돌려보니 이 파일에서 **173건**을 잡습니다 — 스팬 검증, `source`↔`text` 결합, 단서 일치, `persistent` 문제, 기구 끝 위치까지.

`precheck.py` 가 새로 더하는 것은 **정말로 빠져 있던 것만**입니다:

| 추가 검사 | 건수 | 비고 |
|---|---|---|
| enum 범위 (`vocabulary.py` 대조) | **0** | 이미 깨끗합니다. 0이라는 사실 자체가 정보라 남겨둡니다 |
| `derived_from` 가 실제 id 를 가리키나 | **0** | 〃 |
| 과잉명세 라벨 (`left_`, `normal_`, `tip_`) | **94** | 이게 진짜 구멍이었습니다 |

### 극성이 반대였던 검사 하나

`validate.py` 는 명제가 0개면 `no_propositions` 로 지적합니다. 그런데 **섹션 필러는 비는 게 맞습니다** — 원본 리포트에 없는 문장이니까요 (근거는 [검수 문서](../docs/PROMPT_DEFECTS_Prompt_test_reviewed.md) A장). 그래서 필러일 때는 이 지적을 끄고, 반대로 **필러인데 명제를 만든 경우**를 error 로 잡습니다.

> 결과: 발화 1,565건 중 214건에 기계적 지적 267건. **나머지 1,351건은 기계가 볼 수 있는 한 깨끗합니다.**

## 3. ② `audit_records.py` — 읽어야만 아는 것

### 가장 중요한 설계: 명제를 보기 **전에** 문장을 읽게 합니다

이 감사에서 제일 값진 코드는 `dropped`(문장에 있는데 JSON 에 없음)입니다. 그런데 **가장 망가지기 쉬운 코드**이기도 합니다.

문장과 명제 목록을 나란히 주면, 모델은 **주어진 목록을 확인하는 방향**으로 읽습니다. "없는 것을 찾아라"가 과제인데 앵커링이 걸려서, 목록에 없는 것은 아예 안 보이게 됩니다.

그래서 답변 형식을 이렇게 강제합니다:

```
STEP 1  문장만 읽고, 이 문장이 주장하는 것을 claims 에 전부 나열하라
STEP 2  이제 명제를 보고, claims 와 하나씩 짝지어라
           짝 없는 claim  → dropped
           짝 없는 명제   → hallucinated
STEP 3  짝지어진 것들을 필드별로 검사하라
```

`claims` 가 응답 스키마에서 **맨 앞**에 있습니다. 모델은 키를 순서대로 생성하므로, **판정이 존재하기 전에 나열이 먼저 쓰입니다.** 순서를 바꾸면 이 장치가 조용히 사라집니다.

그리고 `claims` 는 버리지 않고 저장합니다 — 준비운동이 아니라 **검증 가능한 증거**입니다. 나중에 "모델이 이 문장에서 무엇을 읽었는가"를 사람이 직접 볼 수 있습니다.

### 모호한 코드에 타이브레이크를 줬습니다

"필요하면 warning 을 붙여라" 같은 지시로는 두 판정자가 절대 일치하지 않습니다. 그래서:

- **`bad_warning`** — warning 을 붙여야 하는 조건을 **정확히 3개**로 닫았습니다 (한정 부정 / 하한 명시 / 판독 제한). 그 외의 누락은 `bad_warning` 이 아닙니다.
- **descriptor type** — 11개 타입에 **우선순위 순서**를 줬습니다. 먼저 맞는 것이 이깁니다. `focal` 은 extent 라고 못박았습니다(한 부위의 얼마만큼이지, 어느 부위들인지가 아니므로).
- **부사** — "보통 변화를 수식한다"를 **위치 검사**로 바꿨습니다. *"부사가 비교 단어나 부정어에 붙어 있으면 그 필드의 것"*. `Slight blunting..., stable` 에서 "Slight"는 blunting 에 붙어 있으므로 severity 가 맞습니다.

### `abstain` 과 `severity`

`ok` / `flagged` 둘뿐이면 임계값을 걸 수 없습니다. 셋을 추가했습니다:

| 칸 | 뜻 |
|---|---|
| `status: abstain` | 문장이 진짜 애매하다. **기권은 공짜지만, 자신 있는 오답은 사람의 시간을 씁니다** |
| `confidence` | 이 결함이 **진짜인지** 얼마나 확신하는가 |
| `severity` | 진짜라면 **얼마나 중요한가** (blocking / major / minor) |

확신과 중요도는 다릅니다. 하나로만 정렬하면 엉뚱한 것부터 읽게 됩니다. **blocking + high 부터** 보십시오.

### 리포트 단위로 묻습니다

한 리포트의 모든 발화가 한 프롬프트에 함께 들어갑니다. 앞뒤 문장에 걸친 문제(같은 기구를 다르게 부름 등)가 보이려면 그래야 합니다. **233콜**입니다.

단, `wrong_section` 과 `derived_from` 은 **코드 목록에서 뺐습니다.** 둘 다 다른 문장을 봐야 판단할 수 있는데, `validate.py` 와 `precheck.py` 가 이미 정확히 봅니다.

## 4. ③ `goldset.py` — **이걸 건너뛰면 안 됩니다**

> 판정자를 검증하지 않으면, 233개 리포트 결과를 **어떻게 쓸지 정할 수가 없습니다.**

`hallucinated` 와 `dropped` 는 꽤 믿을 만할 겁니다. `bad_warning` 이나 descriptor type 선택은 노이즈가 클 겁니다. **코드별로 다른데, 섞인 숫자 하나로는 어느 쪽도 알 수 없습니다.**

```bash
python3 GPT/goldset.py sample --reports 30   # 라벨링 시트 생성
# ... 시트를 채움 (이 단계만은 이 프로그램이 못 합니다. 사람이 채우는 게
#     이상적이지만, 실제로는 별도 모델 패스로 채워도 됩니다 — 다만 그러면
#     아래 "정밀도"는 사람이 낸 정답 대비가 아니라 모델 간 일치도이고,
#     두 모델이 같은 맹점을 공유하면 실제보다 높게 나올 수 있습니다)
python3 GPT/goldset.py score                 # 코드별 정밀도·재현율
```

### 표본을 무작위로 뽑습니다 — 판정자 출력 기준이 아니라

판정자가 flagged 한 것 중에서 뽑으면 **정밀도만 재고 재현율은 원리적으로 못 잽니다.** 놓친 결함은 표본에 들어올 수가 없으니까요. 그래서 고정 seed 무작위로 뽑습니다.

### 모드가 둘입니다

| 모드 | 라벨러가 하는 일 | 얻는 것 | 비용 |
|---|---|---|---|
| **`full`** | 판정자 출력을 **안 보고**, 모든 발화에 직접 결함을 표시 | 정밀도 **+ 재현율** | 30리포트 = 203행, 실제 몇 시간 |
| `precision` | 판정자가 지적한 것만 맞다/아니다 | 정밀도만 | 훨씬 쌈 |

`full` 안내문에 **"판정자 출력을 보지 마십시오"** 를 명시했습니다. 보고 나면 재현율을 못 잽니다.

### 결과를 읽는 법

작은 표본에서 비율을 그냥 쓰면 안 되므로 **Wilson 구간**을 같이 냅니다. n=12 같은 데서는 교과서 정규근사가 음수 구간을 내기도 합니다.

| 정밀도 | 그 코드의 결과를 |
|---|---|
| 0.9 이상 | **목록**으로 쓴다 — 집계해도 된다 |
| 0.6 – 0.9 | **분류 대기열**로 쓴다 — 사람이 걸러야 한다 |
| 0.6 미만 | **쓰지 않는다** — 프롬프트를 고치거나 그 코드를 버린다 |

구간이 넓으면(0.3–0.9 같은) 중간값이 답이라는 뜻이 아니라 **사례가 부족하다**는 뜻입니다.

## 5. ④ `repair.py` — 판정과 수정을 나눈 이유

한 호출에 "틀린 곳을 찾고 + 고쳐서 내놔"를 같이 시키면 **양쪽으로 편향됩니다.**

| 방향 | 무슨 일이 일어나나 |
|---|---|
| 적게 지적 | 고쳐 쓰는 부담 때문에 애매한 것을 그냥 넘김 |
| 많이 지적 | 수정안을 내놓아야 하니 이슈를 만들어냄 |

나누면 각각 **한 방향으로만** 틀릴 수 있고, 그래야 그 방향을 측정할 수 있습니다.

그리고 **④는 ③에 의존합니다.** 정밀도 0.4 인 코드를 수정하는 것은 노이즈에 쓰는 노동이고, 결과물은 어느 쪽이든 똑같이 말끔해 보입니다.

### 안전장치

- **바뀐 것만 바꾸라**고 지시하고, 모델이 스스로 `changed` 에 변경 목록을 적게 합니다. `changed` 에 없는 차이가 보이면 그건 수정이 아니라 드리프트입니다.
- 제안된 스팬이 원문에 실재하는지 **코드로 재검증**합니다. 모델이 가장 자주 어기는 규칙이라, 사람이 발견하게 두면 안 됩니다.
- **"지적이 틀렸다고 보면 그렇게 말하고 원본을 그대로 두라"**고 명시했습니다. 감사도 틀릴 때가 있는데, 억지로 고치면 그 사실이 가려집니다.
- `jsonl/` 에는 **절대 쓰지 않습니다.**

## 6. 전체 실행 순서

```bash
cd /home/ldh/ReportCXR-Ko
export OPENAI_API_KEY=...

# ① 기계 검증 — 호출 없음, 즉시
python3 GPT/precheck.py

# ② 판정 — 먼저 1개로 스키마 확인
python3 GPT/audit_records.py --limit 1 --dry-run
python3 GPT/audit_records.py --limit 3
python3 GPT/audit_records.py                  # 233콜

# ③ 판정자 검증 ★ 여기서 멈추고 시트를 채움 (사람이 이상적, 실제로는
#    별도 모델 패스도 가능 — 위 4장 참조)
python3 GPT/goldset.py sample --reports 30
#   → out/gpt_records/<arm>/goldset/sheet_full.tsv 를 채운 뒤
python3 GPT/goldset.py score

# ④ 수정안 — ③에서 믿을 만하다고 나온 코드만
python3 GPT/repair.py --verdict dropped --severity blocking
```

## 7. 산출물

| 경로 | 내용 |
|---|---|
| `out/gpt_records/<arm>/precheck.md` · `.jsonl` | 기계적 지적 |
| `out/gpt_records/<arm>/by_report/<환자번호>.json` | 환자별: 발화·claims·필드별 판정·기계 지적 |
| `out/gpt_records/<arm>/flagged.md` · `.jsonl` | 문제라고 본 것만. **최종적으로 사람이 검증할 대상** |
| `out/gpt_records/<arm>/goldset/score_full.md` | **코드별 정밀도·재현율** — 시트를 누가 채웠는지에 따라 "모델 간 일치도"일 수도, "사람 대비 정확도"일 수도 있습니다. 3~4장 참조 |
| `out/gpt_records/<arm>/repairs.md` | 수정 제안. 반영 안 됨 |
| `docs/PROMPT_DEFECTS_Prompt_test_reviewed.md` | 임상 판단이 필요한 것 (의사 검수용) |

## 8. 이 도구가 볼 수 없는 것

**스키마 자체가 모순인 자리는 이 감사로 절대 안 잡힙니다.** 두 값이 모두 합법이면 어느 쪽도 규칙을 어기지 않기 때문입니다.

실제 사례: `pleura` 는 `unspecified` 230 : `bilateral` 32, `lungs` 는 `bilateral` 211 : `unspecified` 81 — 같은 종류의 구조인데 두 라벨이 **정반대로** 기울어 있습니다. 규칙이 없다는 뜻이고, 그러면 이 필드로는 하류에서 아무것도 못 거릅니다.

검수 문서 **E장**에 결정 사항으로 정리해 두었습니다.
